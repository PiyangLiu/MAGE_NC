# Fresh validation-greedy support selection

This directory is an independent implementation for all examples except
Figure 2.  It does not import or read the old `unified_validation_greedy`
selectors, support orders, bootstrap prefixes, or post-hoc support-count
reports.

The common selector is in `greedy_selector.py`.  For each branch it:

1. standardises `eta` using the candidate and validation clouds;
2. creates an eight-point coordinate coverage prefix (centroid, extrema and
   farthest-point coverage);
3. evaluates all validation states with the current finite-support model;
4. finds the worst validation states and the 256 nearest unused candidates;
5. ranks those candidates by normalised distance plus their own current
   thermodynamic residual;
6. appends eight points and repeats until the first prefix satisfying both
   declared mean and maximum validation-score limits.

The returned `selected_M` is produced inside the selector.  It is not inferred
from a test curve, coexistence composition, KKT residual, or flow trajectory.
If the finite candidate pool cannot meet the gates, the report explicitly sets
`target_met: false`.

Run one case or all cases with:

```text
G:\developer\anconda\python.exe run_selection.py --case nonisothermal
G:\developer\anconda\python.exe run_selection.py --case all
```

The output contains a JSON audit, a validation curve, and a compressed support
order for every branch.  Figure 2 is intentionally not loaded or modified.
The liquid-liquid pools are generated by the self-contained regular-solution
teacher in `cases.py` using fixed Sobol seeds.  The final ternary-flow pool
uses the archived offline candidate cloud (1,331 liquid and 1,572 vapor
states) and independent centered Dirichlet/Peng-Robinson validation and test
clouds (4,096 states per branch).  The two flow trajectories remain strictly
downstream checks and are never used to choose supports.
